New initiative to fix the ROOT of the duplicate-SKU / false-OOS mess (see [sku-item-code-duplication](sku-item-code-duplication.md)): a catalog/sync hub between Shopify and ERPNext ("Next"). Decided architecture: **separate app eventually, but started as a bounded module `logistics_portal/catalog_hub/` now**, extractable once Phase-1 write-back makes runtime isolation worth it. Build on `ecommerce_integrations` (reuse its Shopify client), don't replace it.

**Root cause proven (via live Shopify API):** duplication is on SHOPIFY, not ERPNext (0 ERPNext-only dupes vs 6,864 Shopify-level SKU spreads). Two mechanisms: (a) whole product duplicated then one DELETED (JST0672 — stock on a deleted-product sibling, active product's variant empty); (b) product re-imported → variants recreated with new IDs, old variant_ids deleted but ERPNext stock stranded on them, and the product itself often ARCHIVED (J.SHORTS, 57 units under an ARCHIVED product). ERPNext has NO reliable active/closed flag → must mirror Shopify status in.

**Phases:** 0 = read-only status sync + problem dashboard (built). 1 = **BUILT 2026-07-15 (`ee47e6a`)** — `api/catalog_hub/actions.py`: fix_candidates (57 consolidations + 255 reactivations on dev at build time), consolidate(dead, survivor) = one Repack Stock Entry bin-by-bin at source valuation + disable dead item + Comments, reactivate(item) = Shopify `productChangeStatus`→ACTIVE (API 2024-01) + mirror status to all product items; CatalogHub.vue fix panels (green consolidate / amber reactivate, two-tap). Module lives at `logistics_portal/api/catalog_hub/` (moved under api/ in f65dd92 to fix 417). Variant-deleted cases (~208) = unfixable until Phase 2. 2 = onboarding gateway (new products through the hub, dedup-checked, push to Shopify) — the prevention layer, NOT built. Write-back to Shopify is a merchant decision, human-confirmed, never auto.

**Phase A DESIGN DECISION (2026-08-19):** chose **Bulk-Operations sweep as the PRIMARY path over live webhooks** — product status is not latency-critical (minutes fine), and Bulk keeps the whole catalog cheap (Justyol is Shopify **Plus** → ~2x API budget, raisable). So no public endpoint / HMAC / webhook registration / second channel alongside ee. The webhook code stays in the tree but DORMANT (enable later only if a sub-minute case appears, likely Phase B stock). Scope = WHOLE catalog, not stocked-only, because (a) zero-stock ACTIVE = the oversell taps a stocked sweep never sees, (b) DELETED only detectable by ABSENCE from a full export.

**`sync.bulk_reconcile` BUILT 2026-08-19 (`5a208a6`) — the scheduled path (hourly_long):** `_run_bulk_products_query` (bulkOperationRunQuery `{products{...status,variants}}`, polls currentBulkOperation, returns 'BUSY' if one already running), `_parse_bulk_jsonl` (handles `__parentId` variant-line flattening), `bulk_reconcile` (diffs export vs all mapped items, writes ONLY drift via set_value update_modified=False, batched commit/500, REFUSES to act on an empty export so it can't mass-flip to DELETED), `trigger_reconcile` (manager-gated manual, enqueues long). Scale on prod: **176,001 mapped items / 26,549 products; 157,306 never-synced** → FIRST run is a one-time ~150k-write backfill (run off-peak), then diff-only. NOT whitelisted/role-gated (scheduler runs it as Administrator). Fields unchanged (custom_shopify_status/variant_live/synced_on).

**ee inventory push mechanics (read from bytecode 2026-08-19):** `ecommerce_integrations.shopify.inventory.update_inventory_on_shopify` (scheduled freq "All", ~every tick; `update_erpnext_stock_levels_to_shopify=1`). `get_inventory_levels`: `FROM tabEcommerce Item ei JOIN tabBin bin ON ei.erpnext_item_code=bin.item_code WHERE bin.warehouse IN (<mapped>) AND bin.modified > ei.inventory_synced_on` — so it pushes ONLY items that (a) are mapped in Ecommerce Item, (b) have a Bin, (c) whose bin changed since the per-item watermark. Qty pushed = `get_total_stock_for_location` = `SUM(actual_qty - reserved_stock)` over mapped warehouses (available, NOT raw actual; NOT per-bin clamped → can go negative on phantom-reserved items). Consequence: any unmapped / un-binned / unmoved product is invisible to ee forever → its Shopify number is frozen (but that's mostly the external-location products anyway). ee can NEVER re-inflate a manually-set number (it only pushes real available, only on bin movement). Phase B must match this math or take over ee's push (turn off the flag) to avoid a flip-flop war on the ERPNext location.
