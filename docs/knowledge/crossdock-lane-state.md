**Measured 2026-09-30 on prod.** The design answer to "where should cross-dock live" was already built before this session asked the question — do not re-propose it.

**What exists and is correct:**
- `Cross-dock - JM` warehouse (parent `Soft Warehouse - JM`): `is_rejected_warehouse=0`, NOT in `lp_excluded_zones`, NOT in `get_rejected_warehouses()` → genuinely pickable. Contrast [receiving-zone-pickable](receiving-zone-pickable.md).
- `api/crossdock_in.py` — supplier-first receiving lane: one submitted PR per PO into `Cross-dock - JM`, rates from the PO, units RESERVED to their own order via SRE, PO `custom_purchase_status` / item `custom_received` / SO item `custom_status` written directly (no save cascade). Built because the PR used to be posted ~9 days AFTER the order shipped.
- `api/crossdock_pickup.py` — the reverse leg: hands returned cross-dock goods back to the supplier out of `Return Zone - JM` via `make_return_doc`, never off a shelf.
- `warehouses.warehouse_settings()` already surfaces the ee veto as a `vetoed` flag per zone, precisely so the portal toggle "is not a lie" — but it is READ-ONLY there.
- **`po.custom_sales_order` is healthy: 2,500 of 2,534 POs = 98.7% filled.** The standard ERPNext `Purchase Receipt Item.sales_order` IS mostly empty, but that does not matter — the portal keys off its own custom field. Do not "fix" `pri.sales_order` as a prerequisite; that was a wrong conclusion earlier in the same session.

**The lane works — do not read the raw bypass count as adoption failure.** Cross-dock-supplier, order-linked receipts landing in `Receiving Zone - JM`: **2,352 receipts / 2,946u PRE-lane (before 2026-09-26)** vs **5 receipts / 3u POST-lane**. A window starting 2026-09-20 straddles the launch and makes the leak look like ~77%; it is not. `redazaari47@gmail.com` posts BOTH lanes (25 receipts into Cross-dock, 84 into Receiving) — one person using two doors, so it is a code-gating question, not training.

**Real remaining holes:**
1. **13 suppliers / 1,698 POs** are order-keyed (`custom_sales_order` set) but their Supplier is NOT `custom_fulfillment_model='Cross-dock'` → invisible to `crossdock_in._EXPECTED`, so they fall through to Goods In. Only 17 suppliers are flagged Cross-dock, 20 Fulfillment, **366 blank**.
2. **`api/purchasing.py` (Goods In) has ZERO cross-dock awareness** (grep for crossdock/custom_fulfillment_model/custom_sales_order returns nothing). It lists ALL open POs and `defaultTarget = RECEIVING_WH`, so a cross-dock PO can still be received into Receiving Zone.
3. `custom_fulfillment_model` is only ever READ (4 refs, all reads) — no portal screen writes it. Classification lives on a Desk field; same family as [desk-decisions-leave-no-portal-fields](desk-decisions-leave-no-portal-fields.md).
4. **2,307 pre-lane orders** have their goods sitting in Receiving, which went unpickable 2026-09-29 — this is the true source of the 55 starved September orders, not a missing `arrived` state.
5. `zones.py` still lists `Receiving Zone - JM` as a restock SOURCE_ZONE, and `audit.py:533`'s comment still asserts Receiving "IS pickable" — stale premise, though the `staleReceiving` radar itself still functions.

**Late pieces for orders that already left — CORRECTED 2026-10-01 (commit `fa994a2` replaces `9679cd5`):** 922 cross-dock POs were open whose order had already shipped/delivered/returned. `allow_negative_stock = 0` on this site, so every such Delivery Note took a piece ALREADY on the books (usually another order's) — receiving the PO with nothing in hand creates a phantom. The earlier "paperwork receipt nets to zero, route to the DN's source bin" idea was WRONG and is removed. Now: `purchasing._paperwork(po)` → {so, status}; `post_purchase_receipt(..., piece_in_hand)` refuses unless the counter confirms the piece is physically there (else purchasing closes the PO — supplier delivered fewer pieces than orders); normal target; `_owed_to(items)` names waiting orders for items nothing on the floor covers (UNION of SOI and Packed Item lookups: 1 ms vs 305 ms). Cross-dock in returns `order_left` (status + owedTo) instead of bare "not waiting".

**Chain-shift victims:** pieces received into shared Receiving with no per-order hold get taken by the next order for the same item. Traced on Awani board BA10687-25 (`48997925781758`): #261946's piece shipped with #262269 (26/9), #262269's with #262762 (29/9); #262762's PO open, #261946 Pending with PO "received" and nothing to pick. 3 such stranded waiting orders on 2026-10-01: #261946, #262107, #262281. The Cross-dock in lane (receive into Cross-dock - JM + SRE per order) prevents new ones.

**Late owed piece routing (2026-10-01, 0e3f589):** Goods In now receives a late cross-dock piece that a waiting order is owed (plain SO line; bundle components consume a unit unreserved) into `Cross-dock - JM` with an SRE for the oldest waiting order via `crossdock_in._reserve`. Verified on prod: #262762's Awani board → #261946 (soi 5207n60d3s) first, then #263168. SREs on `reserve_stock=0` SOs work (2 live lane SREs).

**Unconfirmed POs block the lane (2026-10-01):** agreed cycle (Ahmed, Supplier sessions 09-23/24): PO is submitted only after the SUPPLIER confirms in supplier_portal (`supplier_portal.api.crossdock._settle_purchase_order`), not when our team confirms. It failed two ways: (1) suppliers don't answer — 117/140 lines since 09-15 Expired, yet they deliver; (2) when they DO answer, settle runs as the supplier user and ee's PO on_update re-saves the SO without ignore_permissions → PermissionError rollback (#262698, #262949, #263193). Fixes: supplier_portal branch `crossdock-po-settle-sweep` (d633987, NOT merged to main — Ahmed to merge/deploy) settles inline only if caller can write SO, else the */5 sweep settles answered orders (1h retry throttle). logistics_portal 945c4ff: Cross-dock in `unconfirmed` reason + "piece is here — confirm for the supplier" (`confirm_by_delivery`) runs settle under the receiver's own rights (Reda has PO submit + SO write). 20 waiting orders were stuck, 15 with NO PO at all. Running set_user("Administrator") in a supplier request was refused by the auto-mode classifier as privilege escalation — don't retry that design.
